# 长对话的上下文预算与空回复

2026-10-14 另一次排查确认：新消息的规划在约 2.5 秒内完成，但成员正式回复以 `length` 停止、只生成 1 token。
这与此前规划超时是两条不同的故障路径。系统将该新消息交给另一成员后完成；前一条已成功的回复没有被撤销。

## 原因

托管成员的内存会话累积历史请求、工具结果和回复，群聊的新请求还会携带当前的共享对话背景。
运行时此前没有在每次模型调用前检查输入预算。当前自定义模型适配器的元数据使用 128,000 token 上下文窗口；
底层 pi-ai 会根据该窗口及历史 usage 计算可用输出空间，空间不足时把 `max_tokens` 降至最小值 1。
这里的窗口是客户端配置，不能据此推断服务商模型的真实能力上限。

旧的空回复恢复还会追加一条新的用户提示，继续增加输入；群内失败提示没有区分上下文过长、输出上限和超时。

## 处理

- 每次托管模型请求及工具续接前，按照模型元数据检查预算，计算系统提示、工具定义、消息和图片开销，预留输出及安全余量。
- 结合文本估算与已有真实 usage 检查是否超限。估算覆盖中文，但不是精确 tokenizer，图片开销也是估计值。
- 需要缩短输入时，只从本次发送内容中移除完整的旧用户回合；当前请求及其工具调用/结果链完整保留。
  系统提示、权限和工具定义不通过裁剪来降低；原聊天记录、长期记忆及会话原始 usage 不删除。
- 移除旧回合后，只在发送副本中清除旧 usage，否则 SDK 仍会按裁剪前的高用量把输出压成 1 token。
- 提示模型有旧回合被省略，不能假装知道被省略的信息或重复已完成操作。这是确定性的历史裁剪，**不是语义总结**；
  被省略的旧信息不会全部存在于本次模型请求中，缺失的必要资料仍需读取或澄清。
- 当前请求及其工具链本身过大时，明确返回上下文预算错误，不悄悄截断当前任务、不拆开工具调用与结果，也不自动重做工具。
- 空回复最多恢复一次，移除空助手占位后从当前用户请求/工具结果继续，不追加新的用户提示。
  有部分文字但以 `length` 结束的结果也明确标记为不完整。
- 群提示指明失败的是“这条新消息”，并分别显示上下文、输出额度、超时、认证或限流等类别，不公开服务商原始错误正文。

这不提供无限上下文，也不改变本地 Codex 等 CLI 自身的上下文策略。自定义模型窗口的自动发现及语义摘要仍是后续独立工作。

## 成本影响

预算判断和裁剪都在本地完成，不新增摘要模型调用。空回复恢复次数仍最多一次。
减少重复输入及无效重试，通常有利于降低有效交付的总成本，但不是每条消息更便宜的保证：

- 正常回答会比只生成 1 token 的失败请求使用更多输出 token；输出上限不是固定消耗量。
- 移除旧前缀可能降低缓存命中率。输入总量下降与缓存单价变化需要结合实际服务商计费评估。
- 保留的当前请求、必要工具链和正常产出仍按服务商规则计费。

## 验证方式

自动测试通过真实 SDK 和模拟 HTTP 响应复现：同一上下文在处理前请求 `max_tokens=1`，处理后恢复为 8192，
工具调用与结果配对保留，原上下文及 usage 不变。同时覆盖中文输入、窗口差异、当前任务过大、空回复恢复和安全的错误提示。
